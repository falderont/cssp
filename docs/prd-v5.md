# CSSP — Product Requirements Document (v5)
## From Prototype to Production Build: Site Hierarchy, Billing/Invoice Interface, Integration Adapter Design

**What changed from v4:** three things, all confirmed directly in the request that triggered this round. (1) The facility model gains an explicit **Region → Facility (Site) → Building** hierarchy — v4's flat `Facility` didn't model a provider with facilities grouped by region or a site with multiple buildings. (2) A **customer-facing Billing/Invoice interface** joins the MVP scope — v4 explicitly ruled out "any actual invoicing/billing engine," and that's still true: this is a read-only surface over the provider's existing billing system (NetSuite/Stripe/ERP), not a system that generates or reconciles invoices. (3) The project moves from mockups + a mock-data prototype to a **real full-stack build** — Next.js + PostgreSQL (with row-level security enforced, not just designed) + Prisma, replacing the disposable prototype's in-memory data with an actual multi-tenant database, auth, and adapter layer. `docs/prd-v4.md` remains the reference for everything unchanged; this document only covers deltas plus the integration research that grounds the adapter design.

## 1. Site Hierarchy (extends v3 Section 4 / v4 Section 8)

`Facility` (a data center site — v3/v4's unit of site-scoping for Visitors, Tickets, Incidents, Remote Hands) now sits under an optional `Region` (a provider's geographic grouping — e.g., "Southeast Asia," "US East") and owns zero or more `Building` records (a site with more than one physical building — common at larger campuses). Nothing that was site-scoped in v4 changes scope: a `Building` is a sub-reference on entities that need it (Visitor Management's badge/destination field, BMS Telemetry's per-building readings) rather than a new scoping boundary — adding a scoping level under Facility would ripple into every module's access-control logic for a distinction (which building on a site) that only a couple of modules actually need. `Region` is purely a grouping/roll-up convenience for a Global Admin or provider ops managing many sites; it does not gate access on its own — site enrollment still does that, per v3 Section 4.

## 2. Billing / Invoice Interface (new module, in MVP)

**What it does:** the enterprise account's Global Admin (and, per-site, a Site Contact for their own site's charges) can see invoices issued by the provider — status (Draft/Issued/Paid/Overdue), line items, period, total, and a downloadable copy — inside the same portal where they already track tickets and remote hands. **What it deliberately does not do:** generate invoices, calculate tax, process payments, or reconcile with accounting — that stays in the provider's existing billing/ERP system (typically NetSuite, Stripe Billing, or a colo-specific billing platform), consistent with the project's core positioning (Section 2 of v2: consolidate, don't replace). Research into how colocation providers actually run billing today (NetSuite + Stripe, connected via native connectors or iPaaS, is the common pattern) confirms invoices are system-of-record data that lives elsewhere; CSSP's job is to pull a read model of it into the same place the customer already looks, the same relationship it has with DCIM/CMMS/BMS.

**Why now and not deferred like v4 held it:** Remote Hands (v4 Section 6) already tracks `billable_minutes` specifically because a provider's billing process needs it and currently reconstructs it manually — that data point is dead weight if the customer can log billable work in the portal but then has to go somewhere else entirely to see what it was billed as. Surfacing invoices (even read-only, even sourced from a mock adapter until a pilot's real billing system is known) closes that loop.

**Data model:** `Invoice` (enterprise_account_id, facility_id nullable [site-level vs. consolidated], period_start, period_end, status, total_amount, currency, issued_at, due_at, external_ref [the billing system's own invoice ID]), `InvoiceLineItem` (invoice_id, description, category [recurring/remote_hands/one_time/other], quantity, unit_amount, amount, linked_remote_hands_task_id nullable). Same access-control posture as v4 Section 9's `billable_minutes`: visible to the requesting enterprise account only, never to peer customers.

## 3. Integration Adapter Design (research findings)

Every non-native module in CSSP (Visitor Management's access-control step, Incident sourcing, BMS Telemetry, and now Billing) is built behind an adapter interface with a **Mock** implementation for the MVP/demo and a documented contract a real integration would implement later — this was implicit in v2's "Manual/DCIM/BMS Adapter" framing; this build makes it a literal interface in code, consistently, for every external-system boundary:

- **Access Control (PACS):** researched Lenel OnGuard and Genetec Security Center, the two PACS platforms visitor-management integrations target most often. Wire-level, OSDP is now the SIA-recommended protocol over legacy Wiegand for new hardware, but that's a concern for the PACS vendor and the card reader, not for CSSP — CSSP integrates at the system/API layer (issue a temporary credential for a visitor's visit window, revoke it after, reflect check-in/out back), the same shape regardless of which PACS or wire protocol sits underneath. `AccessControlAdapter`: `issueVisitorCredential(visitor, facility, window) → credentialRef`, `revokeCredential(credentialRef)`, `syncCheckInStatus(credentialRef) → status`.
- **DCIM / CMMS (incident sourcing):** confirmed the v2 assumption — modern DCIM/BMS/CMMS integration runs through open REST APIs and protocol gateways (BACnet, Modbus, SNMP, MQTT) that normalize device-level data before it ever reaches an application layer like CSSP. CSSP's `IncidentSourceAdapter` therefore models the *normalized* shape (facility, type, status, window, description, source) regardless of whether the source is a human publishing manually (the MVP default, per v2 Section 8) or a future DCIM/CMMS webhook.
- **BMS Telemetry:** same normalization point as above — a `BmsAdapter.getFacilityTelemetry(facilityId) → readings[]` interface returns normalized power/temperature/humidity readings, whatever protocol gateway produced them upstream. Still optional/stretch per v3/v4; implemented here as a thin, clearly-labeled module so the interface exists and is demoable, not as a promise of real BMS connectivity.
- **Billing:** per Section 2 above, `BillingAdapter.listInvoices(enterpriseAccountId) → Invoice[]`, `getInvoiceDetail(invoiceId)`.

## 4. Build Decision

v4's prototype README explicitly scoped the mock-data React prototype as disposable and named the production stack: Next.js, PostgreSQL, Prisma, a managed auth provider, with an adapter layer for DCIM/CMMS/BMS. This round builds that stack for real rather than iterating the prototype further: `webapp/` is a genuine multi-tenant application — Postgres with row-level security policies keyed on `organization_id` (v3 Section 3's non-negotiable, now actually enforced by the database for a non-owner application role, not just documented as an intention), real authentication, and the adapter layer above. The `prototype/` and `mockups/` directories are kept as-is for design history; they are not grown in place, per the prototype README's own framing.

## 5. Open Questions (extends v4 Section 12)

Whether `Region` needs its own admin role (a "regional manager" scoped to a subset of a provider's facilities) or whether existing provider roles suffice with a facility-multi-select — leaning toward the latter for MVP, revisit if a design partner's org chart needs it. Which real billing system a pilot actually runs (NetSuite+Stripe is common but not universal in this market) stays open until a pilot is signed; the adapter boundary means that choice doesn't block building the customer-facing surface now.
